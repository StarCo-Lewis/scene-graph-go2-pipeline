# D3-619 客户端使用手册

更新：2026-10-23。中文界面，英文任务与工程 JSON。适用本工程配套 TCP 客户端及狗端网桥。

## 1. 先了解操作顺序

**输入任务 → API 规划通过 → 已有当前起点时自动填写 BBOX 外侧 0.4 m 候选点 → 人工核对 → 握手连接 → 确认后发送一次 → 查看反馈与终态。**

左侧列表仅浏览场景或辅助填写示例，不是指令约束，不必选中与命令相同的物体，也可不选择。目标以指令经 LLM 对象绑定后的结果为准；发送前仍需核对模型实际绑定的 ID。

已有工程 JSON 时可直接加载，从填写当前起点开始，不必重新调用 LLM。

本次接入不改导航控制器。原来的前进 0.5 米现场日志证明原狗端 ROS2 链能运动，不证明新 TCP 链已经跑通，也不能把当时 `blocked` 当作到达。新网桥仍需现场部署联调。

拔掉网线后，可查看场景、加载计划、生成候选点、预览和做离线检查；不能验证狗端握手或运动。离线测试不等于真机 dry-run。

## 3. 输入任务后怎么做

### 推荐：直接在窗口配置 API 并规划

不需要手动复制 WSL 命令，也不需要预先启动队列后端；底层仍复用本机已安装的 WSL 环境。

1. 打开“API 规划”页，填写 API key（掩码显示）、模型和 Base URL。默认沿用 `qwen3.8-flash` 和 `https://dashscope.aliyuncs.com/compatible-mode/v1`。
2. WSL 发行版留空表示默认发行版；若规划环境装在指定发行版，填其准确名称。在“连接 / 规划环境 / 反馈”页核对原有规划 Python、embedding Python 和模型目录。
3. 回“任务与场景”页，直接输入英文导航指令。**点击“调用 API 规划当前指令（不执行导航）”**，无需先选列表物体或点准备任务。API 页也有相同功能按钮。
4. 确认弹窗中的服务地址、模型、目标、指令以及 API 费用/数据发送提示。此时才启动 WSL 并调用完整规划流程。
5. 查看“详细日志”的分解、对象绑定、技能检索、技能矩阵和校验进度。窗口自动加载工程 JSON，但规划没完整通过前不允许发送导航。
6. 规划完成后，若已填写当前实际起点，窗口会自动填入 BBOX 外侧 0.4 米候选点；否则按提示填写起点，随后自动计算。核对目标 ID、坐标和路线，按第 5 节确认发送。**自动填入不等于授权运动。**

密钥不写任务 JSON、不放进进程命令行；通过子进程标准输入传给 WSL，仅提供给规划子进程的环境。新入口的控制台日志会遮蔽该密钥。重启窗口需重新填写；“清空窗口中的密钥”不撤销已启动的 API 请求。

该入口调用原 `real-scene-plan` 流程，不用模型直出坐标替代原流程，保留对象绑定、技能参数与计划校验；技能绑定接收当前加载技能库的完整清单，不再进行 cosine/top-k 预筛选。自定义地址仅接受无内嵌凭据的 HTTPS；场景与任务会发送到该地址。其它兼容服务/模型需另行验证，不能保证改名即兼容。

规划失败只显示失败并保留日志，不生成预设替代计划、不自动补跑整轮。单次请求的重试仍沿用原管线。重新点击会创建一份新任务并再次计费，请先查清失败原因。

拔网线不影响通过 Wi-Fi/互联网调用 API；但没有有线连接不能握手/发送到狗。关闭窗口不保证停止已启动的 WSL 规划，可能继续计费，程序会提示。

### 备用：手动 WSL 命令 / 队列方式

1. 可选：在“任务与场景”页浏览物体，按 ID/英文标签搜索，例如 ID 179 的 round table。浏览选择不会成为任务约束。
2. 输入英文任务，或点“用所选物体填写示例”。例如 `Navigate to the round table (ID 179). Do not manipulate any objects.`。只有点击示例按钮才会把列表物体写入指令。
3. 点“准备任务 / 生成命令”。只写任务文件，此时不调用模型、不运动。
4. 用以下任意一种方式规划，不要对同一任务同时运行两种方式。
5. 等待结果，核对目标 ID、动作、任务检查、静态检查。检查失败或目标不对时停止，不手改动作来冒充模型通过。

**方式 A：一次启动 WSL 规划后端，后续窗口提交。** 你在 WSL 规划终端设置密钥：

```bash
read -r -s -p 'DashScope API key: ' DASHSCOPE_API_KEY
printf '\n'
export DASHSCOPE_API_KEY
```

到“连接 / 规划环境 / 反馈”页核对 Python、embedding Python 和模型路径，点“复制规划后端启动命令”，在上述终端粘贴执行。后端在线后，在同页点“备用：提交已准备任务给手动启动的 WSL 后端”，确认 API 费用提示。窗口会观察规划结果。

**方式 B：每次手动运行。** 不启动常驻后端，点“复制 WSL 规划命令”，在已设置密钥的 WSL 终端运行。

规划网络/API 与连接狗的有线网络是两条链路。只有明确点击 API 入口才由窗口启动 WSL，备用方式仍由你手动启动。当前执行入口只接受一条 `navigate_to_object`；多目标、抓取、放置及未完成子任务不会被静默删掉后继续执行。

## 4. 导航点映射：不是物体中心

在“导航点映射 / 控制”页：

1. 填狗**现在**的 `x, y, yaw`。米、弧度、左转为正，必须是已对齐场景系下的实际起点；不能每次填零，也不能把上次目标当实际位置。
2. 规划通过且起点已填完整后，窗口自动填写候选点，默认在当前起点所在一侧、朝向目标物体。也保留“按 BBOX 外侧 0.4 m 生成候选点”按钮用于显式重算。
3. 核对点与路线是否落在墙、桌子或其它障碍物内。必要时用现场确认的外侧点替换；手填/导入点在预检时要求距目标 BBOX 至少 0.4 米。
4. 点“预览映射（不执行）”，看终点、起点、ID、参数和未完成确认项。

可以在规划前先填当前起点，规划完成后不清空这份输入，但仍需重新确认其实际有效性。起点为空时不会默认零点。改变起点会清除旧的自动候选点并重新计算，取消相关确认项；手动修改/导入的目标不会被自动覆盖。收到服务端终态后，只要 `final_pose` 有效就更新起点，包括位置未达容差、取消等未成功到达的情况。失败仍暂停自动队列；没有有效位姿、定位丢失或断线时才清空起点。不回填旧零点或计划目标。

新建任务不再含列表给定的 `target_element_id` 参考答案。规划后的动作仍必须包含场景中存在且有效的目标，并与对象绑定一致。系统 1 每次规划一条导航；系统 2 可以规划多条有序导航。混有抓取等其他动作的计划不会被截取后执行。结构检查通过不能证明模型一定正确理解语义，目标歧义或误绑定仍需核对。

当前导出的是 AABB，使用 XY 水平投影：

```text
low  = bbox_center.xy - bbox_extent.xy / 2
high = bbox_center.xy + bbox_extent.xy / 2
q = 当前起点在 [low, high] 矩形上的最近投影点
u = (当前起点.xy - q) / ||当前起点.xy - q||
导航点.xy = q + 0.4 * u
导航点.yaw = atan2(中心.y - 导航点.y, 中心.x - 导航点.x)
```

`bbox_extent` 为完整边长，不是半长。角点方向的欧氏间距为 0.4 米，不是 X、Y 各加 0.4 米。起点位于实体物体矩形内/边界时自动生成拒绝。地板/地面类目标（floor、floorboard、flooring、ground、ground plane）允许起点位于范围内：选择最近边界，再向外延伸 0.4 米；距离相同时按 +X、-X、+Y、-Y 顺序选择。仍需核对候选点和路线，语义标签不证明地面可通行。

**这里的间距是导航参考点到 BBOX 的距离，不是机身边缘净空保证。** 尚未计算机身轮廓、障碍栅格或可达路线。小物体在桌上时，离它 0.4 米可能仍在桌内。不能因为数值合法就运动，必须核对支撑物、墙和周边环境。场景图投影不等于避障地图。

旧计划 `standoff_m` 可能仍为 0.6；源文件保持不变，本次采用你新指定的 BBOX 外侧 0.4 米。原值、新规则及覆盖依据写入 `dispatch_config.json/navigation_point_policy`，并非暗改原计划。

也可导入导航点表。以下仅结构示例，`null` 要换成实测/确认值，否则不能通过：

```json
{
  "schema_version": "navigation_points_v1",
  "coordinate_frame": "d3_619_slam_world_x_forward_y_left_z_up_m",
  "source_graph_sha256": "4f79f1b86ad3335f7a100b65987ad0d4017bea0b78f46deec97d4c31652e1174",
  "points": {
    "179": {"x": null, "y": null, "yaw": null}
  }
}
```

## 5. 连接、确认、发送

前提：导航组已启动正确地图的 CAPO、真实控制出口和导航 Action，配套网桥已部署。只有网线和端口连通还不够。

1. 连接网线，在“连接”页核对 `192.168.123.18:8888`。电脑有线地址按现场约定 `192.168.123.100/24`，默认网关留空，不改 Wi-Fi。
2. 在控制页填网桥共享口令，点“握手连接（不发送导航）”。不是 DashScope API key，窗口只在内存保存该口令。
3. 核对协议、frame、Action 就绪、允许转发、非忙状态。网桥状态不证明 SportSink、定位或实际限速已验证。
4. 逐项人工确认：真实起点、场景系对齐、停靠点和路线、固定参数、看护/物理急停、服务端初始对齐策略，以及真实 SportSink/CAPO/ActionServer。改起点或终点会取消对应确认。
5. 预览确认没有阻止项。
6. **点“确认后发送一次导航”，再次同意真实运动弹窗，此时才会发导航目标。** 不自动往返，不自动重试，不自动执行下一条。

保持当前用户指定请求值，不自动调参（2026-10-23 更新超时为 120 秒，保留已指定的速度值 0.5）：

| 参数 | 值 |
| --- | --- |
| `pos_tol` | 0.05 m |
| `yaw_tol` | 0.17 rad |
| `timeout` | 120 s |
| `max_speed` | 0.5 m/s |
| 起终点 `z, roll, pitch` | 0 |

不修改 CAPO 比例、末端接近、路径跟随、避障逻辑或节点启动配置。`max_speed` 只是请求字段，不能保证实际速度上限。通信看门狗仅在失联/缺少终态时请求取消，不调整控制器、不重放任务。

场景轴约定前 X、左 Y、上 Z。第一次目标会依现有服务策略按起点对齐里程计；后续不应重新假设零点。**修改 frame 名称不是坐标变换。** 原临时零点前进测试与 D3-619 的坐标注册需现场确认；未确认不能发。

## 6. 发送后看什么

任务页显示实际反馈位姿的轨迹，不用动画模拟，不宣称已实现规划路径/障碍栅格展示。位姿为里程计估计，不是独立真值；旧反馈会标为过期。

| 消息/结果 | 意义与操作 |
| --- | --- |
| 等待接收、`goal_accepted`、feedback | 不是到达；继续现场看护，不重复发 |
| ROS 成功终态且 `success=true, reason=arrived` | 服务端报告到达，仍需核对实际停止和位置 |
| `blocked`、超时、失败或取消终态 | 不自动重试，先确认停止、查原因、重测起点 |
| 断线、无终态、执行未知 | 不能认定没动/已停，必要时物理急停，先查清状态 |
| 取消已应答 | 只确认取消请求应答，不等于物理停止 |

“请求取消”、关闭窗口、拔网线都不是物理急停。操作人员全程握持遥控器。

系统 1 成功终态后接续有效实际位姿，下一次重新核对检查项。系统 2 依整队授权自动接续，停留 10 秒后发送下一段。失败、取消、缺少有效终态位姿或断线会暂停队列，不自动重试。未知状态禁发新目标。“人工核对后解除本地未知状态”只解除本地阻止，不停止狗，也不重置狗端坐标系或清除狗端锁。

## 7. 狗端网桥一次性部署

由能操作狗端的人部署一次，之后电脑窗口日常控制不需要 SSH。将以下两文件放狗端同一目录，例如 `/home/unitree/nav_ws/nebula_bridge/`：

```text
embodied_pipeline/execution/tcp_bridge.py
embodied_pipeline/execution/tcp_protocol.py
```

依赖现有 Python 3.10+、`rclpy`、`nav_interfaces`、`rosidl_runtime_py`。只转发到 `/nav/navigate_to`，不启动导航、不调用运动 SDK、不在缺包时伪装沙箱。

狗端设置随机共享口令至少 24 字符，电脑填相同值，不放到仓库/聊天/日志：

```bash
read -r -s -p 'FIELD_BRIDGE_TOKEN: ' FIELD_BRIDGE_TOKEN
printf '\n'
export FIELD_BRIDGE_TOKEN

ROS_DOMAIN_ID=0 bash /home/unitree/nav_ws/dogenv_run.sh \
  /home/unitree/nav_ws/nebula_bridge/tcp_bridge.py \
  --bind 192.168.123.18 --port 8888 \
  --scene-frame d3_619_slam_world_x_forward_y_left_z_up_m \
  --runtime-dir /home/unitree/nav_ws/nebula_bridge/runtime
```

上面不带 `--allow-motion`，只允许握手/状态，不转发运动。先核对接口、服务和 D3-619 注册；仅填写场景名不做标定。需要允许运动时，确保没有活动/未决任务，停止这个只读网桥，再用同一命令加 `--allow-motion` 启动。不要重启导航/CAPO或重置原点。启动允许转发也不会自动发目标。

若 8888 已占用，先确认服务归属，由现场负责人协调，不杀未知进程，不使用会重启导航的脚本。另选端口时电脑同步修改。ROS_DOMAIN_ID 按现场日志固定 0，RMW 沿用狗端环境。

协议 `nebula.navigation.tcp.v1`，不兼容未知 `go2_bridge_agent.py` 报文，不自动猜测/降级。共享口令 TCP 没有 TLS 加密，仅用于可信私有有线网，不暴露公网。

异常退出遗留 `runtime/pending_goal.json` 时，网桥下次拒绝启动。先确认狗停止、查清旧目标终态，再人工归档该记录，禁止直接自动重放。

## 8. 日志与恢复

以下路径相对于工程根目录：

- 任务：`outputs/real_scene_runs/field_ui_<时间>_<编号>/task.json`；模型输出在 `planning/`，后端日志 `worker.console.log`。
- 窗口 API 入口另外记录 `api_launch.json`（不含密钥的配置）、`api_result.json`（规划进程结果）和 `planning_owner.lock`（防重复启动记录）。有锁/结果的运行不自动重放，不要删锁来重试同一目录。
- 规划队列：`outputs/field_console_queue/`。不重复提交同任务，不自动补跑；遗留 `worker.lock` 先确认旧进程退出再处理。关窗口不结束 WSL 规划。
- 导航运行：`outputs/real_scene_runs/tcp_navigation_<时间>_<编号>/`。
- `dispatch_config.json`：起点、终点、BBOX 间距政策、固定参数、确认项、源哈希。
- `navigation_request.json`：映射后的接口请求，不是执行成功证明。
- `tcp_events.jsonl`：消息、反馈和请求标识，不含口令。
- `run_summary.json`：收到终态/拒绝后保存，不宣称独立验证物理到达。未知状态可能没有该文件，应查看事件日志。
- 电脑未决记录：`outputs/field_control_state/pending_client.json`；狗端未决记录：网桥运行目录的 `pending_goal.json`。

## 10. ROS2 直连（可选，不经过 TCP 8888）

2026-10-23 增加第二种控制方式。上文 TCP 网桥的口令和部署步骤只适用于“TCP 网桥”模式；ROS2 直连不用网桥、不用 SSH 发送任务，也不自动访问 WSL。仍然使用同一份工程计划、真实起点和 BBOX 外侧 0.4 m 候选终点，不增加本地路径规划。

### 10.1 环境要求与已验证范围

必须用**已经配置 ROS2 的 Python** 启动窗口，该解释器需要能够导入：

- `tkinter`：窗口。
- `rclpy`、`rosidl_runtime_py`：ROS2 客户端。
- 导航组提供并构建的 `nav_interfaces.action.NavigateTo`：须与狗端接口匹配。不是任意同名包。

2026-10-23 检查当前 Windows Python 3.12 时，`rclpy` 和 `nav_interfaces` 均不可用。因此这是“代码已接入”，不是“当前电脑已完成 ROS2 安装”，更不是“真机联调已通过”。不要把狗端 Python 路径填进电脑窗口来解决，也不要假设 `pip install rclpy` 就能完整配置 ROS2。

日志中的狗端为 Ubuntu 20.04 / ROS2 Foxy；电脑此前为 Windows / WSL Ubuntu 24.04。ROS 发行版、Python ABI、消息包和 DDS 互通需要配套验证，不承诺跨发行版直接互通。不自动安装或变更这些环境。

在现场已配置好的 ROS2 终端中，先确认同一个 Python 能导入：

```text
python -c "import tkinter, rclpy; from nav_interfaces.action import NavigateTo; print(NavigateTo.Goal.get_fields_and_field_types())"
```

根据已安装的 ROS2 环境，先加载其环境和 `nav_interfaces` 工作区。然后在工程根目录启动窗口。PowerShell 示例（不是安装命令）：

```powershell
$env:ROS_DOMAIN_ID = "0"
python -m embodied_pipeline field-console
```

Linux/WSL 已配置环境示例（用户自行执行；代理不访问 WSL）：

```bash
export ROS_DOMAIN_ID=0
python3 -m embodied_pipeline field-console
```

直连依赖 DDS 发现与数据通信，不使用界面中的 TCP IP/端口定位服务器。网线、IP 同网段只是前提，还须核对 DDS 网卡、防火墙、ROS_DOMAIN_ID 和中间件环境。狗端使用的 `eth0` 不能直接照搬到电脑；不要复制狗端 CYCLONEDDS_URI 来猜电脑网卡。不自动修改 RMW/网络设置。

### 10.2 窗口操作

1. 确认狗端 CAPO 和导航 Action 已启动、使用正确的 619 地图。此功能不启动或重启它们。
2. 打开“导航点映射 / 控制”，连接方式选择 **ROS2 直连**。TCP 口令框禁用，不需要填写 SSH 密码或 API key。
3. 点击“连接 / 检查（不发送导航）”。仅创建本地 ROS2 客户端、发现服务并检查本地 Goal 字段，不发送测试目标。找不到服务器约 8 秒后报告失败；缺依赖直接报错，不回退其他模式。
4. 看到“ROS2 直连（无 TCP 网桥）· Action=就绪”后，核对真实起点、目标、场景对齐、地图和现场安全。界面中的场景名是本地声明，不是狗端地图/坐标自动核验结果。
5. 确认没有其他 Action 客户端正在发目标。直连只能约束本客户端的任务，无法通过当前接口证明导航服务全局空闲；别同时运行 `group2_action.py` 或另一台电脑发送目标。
6. 点击预览，核对无阻止项，再人工确认发送一次。输入任务、连接成功都不会自动运动。
7. 实时反馈显示实际 ROS2 位姿估计；收到成功终态后仍需核对实际停止。“取消已应答”不是已经停止，关闭窗口或断网也不是急停。

不连接未知 TCP 服务，不自动发现并更改控制方式；切换前必须断开旧连接，未决运动状态仍会阻止重发。

### 10.3 参数和日志边界

ROS2 直连与 TCP 方式使用相同的 16 个 Goal 字段，不改起终点、不添加路线、不自动调整运动参数。当前用户指定锁定值为 `pos_tol=0.05`、`yaw_tol=0.17`、`timeout=120`、`max_speed=0.5`，`z/roll/pitch=0`。修改后须在无活动任务时重启客户端并重新预览；TCP 模式需同步网桥端协议配置，不能只更新界面文案。历史运行 JSON 和已发出的目标不会被改写。

**历史现场日志中最后 `arrived` 的测试用的是 `max_speed=0.3`。当前 0.5 是用户后续指定值，不代表已验证该速度下的真机执行；实际速度上限也不能仅由这个字段保证。**

原 `tcp_navigation_*` 运行目录和 `tcp_events.jsonl` 文件名为兼容历史读取保留；ROS2 直连记录中使用 `transport=ros2_direct` 区分，不表示真的经过 TCP。`dispatch_config.json` / `navigation_request.json` 同样记录该控制方式。

直连另有持久记录：`outputs/field_control_state/ros2_direct/pending_goal.json` 和 `bridge_events.jsonl`。这里复用的是本地单目标状态管理代码，不会启动 TCP 监听。未确认终态时保留 pending，下一次直连拒绝创建新的发送会话；窗口“解除本地未知状态”不会自动删除它。必须先现场确认停止、核对导航终态，再人工归档记录，不要为了恢复按钮删除锁。

窗口正常关闭会尝试取消，短暂等待结果；进程被强杀/电脑断电时无法保证取消送达，仍依赖现场遥控器。无自动重试、无自动往返、无自动下一任务。

## 11. 两种多段导航流程（2026-10-30）

两种流程共用同一个场景坐标系。首次 `s_*` 是狗在该场景中的实测起点；它不一定是 `(0,0,0)`，也不要求狗走回原点。客户端不发送重置里程计命令。后续起点来自有效终态的 `final_pose`，不会拿上一段的计划 `g_*` 冒充实际位置。任务失败不等于位姿无效；系统 1 可以保留失败终态的实际位置，用于人工核对后的新任务。系统 2 仍只有成功到达才自动前往下一目标。

### 系统 1：每次输入一个目标

1. 在“系统 1 · 逐次任务 / 场景”输入 `Navigate to A.`，A 换成实际物体名称或 ID。
2. 调用 API 规划，填写首次起点，在控制页核对停靠点和现场检查项，然后确认发送。
3. A 段结束后，窗口自动接续有效的场景系 `x/y/yaw`；即使结果为 `position_out_of_tol`，也保留有效实际位姿，同时显示任务失败。它仍是定位估计，不是独立测量真值。
4. 再输入 `Navigate to B.`，重新调用 API；新计划保留 A 段实际终态作为本段起点。
5. 核对期间机器人没有被搬动或遥控移动，确认 B 的停靠点后发送。此流程不自动执行下一任务，也不强制停留计时。

### 系统 2：一次输入整条队列

1. 在“系统 2 · 多目标导航”输入 `Navigate to A, then navigate to B.`，把名称换成图中真实目标；也支持明确要求的 A → B → A。
2. 点击“调用 API 生成多目标计划”。仍经过原来的任务分解、物体绑定、技能绑定和工程 JSON 校验，不靠文本切分直接发送目标。
3. 规划通过后，填写首次实测起点，点击“从当前工程计划生成队列”。表格显示每段目标 ID、名称和停靠点。后续候选点的计算可以使用前一候选点选择靠近方向，但实际发送的后续 `s_*` 只使用真实终态反馈。
4. 核对顺序和全部停靠点；选中某一行可修改 `x/y/yaw`。修改后需要重新勾选整队确认。含非导航动作的计划不会被删减后执行。
5. 在控制页完成连接和现场检查项；回多目标页勾选整队授权，点击“确认并启动整条队列”，核对弹窗中的全部目标。
6. 成功到达 A 且返回有效 `final_pose` 后，客户端使用单调时钟计时 **10 秒**，显示倒计时，然后以 A 的实际终态位姿发送 B。每个中间目标都停留 10 秒；最后一段结束后不再发目标。
7. 倒计时期间也可以点击“停止队列并请求取消当前段”。暂停后不自动恢复或重试。失败、取消、位姿缺失、执行状态未知、连接变化均停止后续发送。

队列只在当前窗口会话内有效，不在窗口重启后自动恢复。手动改起点或目标、切换计划/场景会取消剩余队列授权。若停留或规划期间搬动机器人，需要核对并更新原场景系中的当前位置，不能重新填写旧零点。

### 可选：连起点异常时也禁止自动重对齐

已读取导航组仓库 `mission/ros_action.py` 和 `mission/api.py`：正常连续导航本来就是首次建立变换，后续沿用；客户端接续实际终态即可，不需要为此修改或重启狗端。现有 Action 默认传入 `realign_on_mismatch=True`，只有后续起点与定位相差超过 0.20 m 或 15°时才可能重新建立变换。以下补丁只是希望连异常起点也禁止重对齐时的可选项，不是多段导航的前提。

本工程提供 `embodied_pipeline/deployment/configure_first_alignment_only.py`。将该脚本交给狗端操作人员，复制到例如 `~/nav_ws/nebula_bridge/`。在狗端执行：

```bash
# 先查看将要修改的一处调用；不写文件、不连接 ROS、不发目标。
python3 ~/nav_ws/nebula_bridge/configure_first_alignment_only.py \
  ~/nav_ws/nav/mission/ros_action.py

# 核对差异后写入；自动保留带时间戳的原文件备份。
python3 ~/nav_ws/nebula_bridge/configure_first_alignment_only.py \
  ~/nav_ws/nav/mission/ros_action.py --apply
```

脚本仅把 Action 执行入口调用中的 `realign_on_mismatch=self.realign_on_mismatch` 改为 `realign_on_mismatch=False`。第一次 `T is None` 时仍执行首次对齐；之后保留已有 T，包括起点校验不一致的情况，不调整速度、超时、容差或 CAPO 参数。未知版本源码会拒绝修改。

**修改源码不影响已经运行的进程。** 请在机器人停止、无活动目标时，由导航组安排重启导航节点，再开始新一轮导航；不要在 A 与 B 之间重启导航/CAPO。新进程需要重新核对首次起点。如果导航组另有会调用 `align()` 的入口，仍需由导航组确认没有在任务期间使用它；本补丁只覆盖 `/nav/navigate_to` 的 Action 执行入口。

当前 TCP/ROS2 消息没有服务端“变换锁定/启动代次”字段，客户端不能自动证明远端是否中途重启，因此现场必须确认这项状态。当前实现仅经离线回归和界面检查，未据此宣称真机多目标验证通过。


2026-10-30 位姿接续修正：到达判定与位姿有效性分别检查。ROS 终态 4/5/6 中，有限坐标、有效四元数且 frame 为 scene 的 final_pose 可以接续；no_pose、定位丢失/过期、缺失或非法位姿不能接续。失败终态不增加成功段数、不自动跳过失败目标，也不自动重试。重启客户端不自动把历史日志当作当前定位。

### 2026-10-30：取消技能 cosine 预筛选

重启客户端后，新规划使用 `full_inventory_no_cosine_v1`。每个子任务收到当前加载技能库中的全部技能，后续参数、依赖、目标与协议校验仍保留。规划不再启动或要求本地 embedding 环境；旧命令的 embedding 参数仅为兼容保留。界面不再要求填写这些路径。

“完整清单”指本次运行加载的技能库，并不把未对接的硬件能力自动变为可执行技能。此改动避免相似度误筛选，不保证模型选择一定正确；技能输入增加时，API token 消耗也可能增加。

当前客户端、数据采集、执行反馈提案及 Oracle 提案入口使用新策略。冻结的历史输出和独立 legacy/validated 回放引擎保留。旧采集包仍受代码哈希保护，不能混用新代码续跑；需另建新版本实验包。旧 cosine 的 intent-comparison 结果不能作为同策略续跑输入。日志中的 `candidate_policy` 和 `embedding_used` 可用于核对。
