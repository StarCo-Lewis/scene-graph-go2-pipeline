2026-10-30。适用于现场任务工作台的「导航地图 / 轨迹」页。

五份提供材料已保留在工程内：地图和原点示意图在 `embodied_pipeline/ui/assets/navigation_619/`，原始两个 Python 示例和组 2 手册在 `embodied_pipeline/deployment/navigation_view_reference/`。原始文件没有改写，来源哈希见该参考目录下 `source_manifest.json`。

地图是 `619_map_v1_clean_5cm.npz`：400 × 474 格、0.05 m/格，`origin=(-12.851,-12.56)`，`scene_origin=(0,0)`，1 为障碍、0 为自由。它是点云衍生的二维栅格，不包含原始三维 XYZ 点云。程序按 `origin - scene_origin` 定位，row=0 在下边，不镜像 Y 轴。

原点图片注明采集日期为 2026-10-12/13。家具移动不会自动更新地图。图中 (0,0) 不是“任意当前位置”，只有狗在对应位置且头朝 +X 时，起点才是 (0,0,0)。本页不设置起点，不重置坐标系。

## 使用流程

1. 没有活动导航时重启客户端，启动命令仍是 `python -m embodied_pipeline field-console`（在工程根目录执行）。Windows 标准 Python + Tk 即可；新增页面不需要安装 NumPy、Matplotlib、Pillow 或 ROS。
2. 打开「导航地图 / 轨迹」。地图自动载入。点击「实时观察」显示本窗口接收到的数据。
3. 仍在原来的「导航点映射 / 控制」页连接、核对并发送任务。本页不会自行连接、发送或取消目标。
4. 蓝线是服务端反馈的场景系定位轨迹；绿点和箭头是最后收到的位置/朝向；红虚线是实际收到的规划路径；紫色十字是导航图原点。鼠标移动显示导航图 x/y 坐标，黑线为 1 米。
5. 超过 3 秒无位姿会明确显示过期。旧位置留作记录，不代表机器人停止。离线回放明确标为离线，不能当作当前位置。
6. 窗口接续多个任务时，记录会保留在同一个可视化会话。不同任务、断线前后的点不直接连线，避免画出未观测的运动。失败终态照实记录；有有效 final_pose 时显示实际终点。

**坐标对齐限制：**提供的手册明确说导航组场景系与语义图尚未完成对齐核实。因此本页与原有语义物体图分开，不自动叠加语义 BBOX，不用叠图宣称定位误差，更不会修改发送坐标。同名 frame 也不是对齐证据。

## 规划路径与网桥版本

- 原有 TCP 网桥已经传 Action feedback/result，所以更新电脑客户端即可显示实际位置、轨迹和结果。
- 红色规划路径需要狗端同步本次更新的 `embodied_pipeline/execution/tcp_bridge.py`。新版本只额外订阅 `/nav/planned_path`，QoS 为 RELIABLE、KEEP_LAST、depth 100；导航仍由已有 ActionServer 完成。电脑不用安装 ROS。
- ROS2 直连使用同一观察接口，在连接时增加上述订阅。
- 不更新网桥时，界面显示“规划路径未收到”。不会把起终点直线、目标列表或 LLM 输出伪装成狗端规划路径。
- 该 JSON 话题不含 goal UUID，因此路径证据标记为“本请求期间观测到，未独立核实关联”。仅在本连接的活动任务期间转发。不把话题内容用于改变控制、判定到达或调度后续任务。
- 单个消息受现有 64 KiB 协议上限约束。过大消息不转发，图中仍显示未收到；不会截断路径后当作完整路径。可视化丢失不修改导航状态。

更新狗端时：先确认没有活动导航；保留现有文件备份；仅替换网桥脚本，沿用现场既有 token、frame、端口和启动参数。不要为了更新图片功能重启 CAPO 或导航节点。这里只准备了代码，未远程部署。

## 自动保存的文件

首条导航记录到来后，创建 `outputs/real_scene_runs/navigation_view_时间_唯一编号/`。只在数据变化时每 5 秒保存，收到终态后尽快保存，并在正常关闭窗口时补存。硬杀进程可能丢失最近数秒的快照，逐条 JSONL 会先写入。

| 文件 | 内容 |
|---|---|
| `events.jsonl` | 原始反馈、路径、终态、断线与请求记录；保留服务器时间（若有）及客户端接收时间 |
| `map.npz` | 本会话使用的实际地图副本 |
| `trajectory.npz` | `traj(N,3)`、`traj_t`、`segment_ids`、阶段时序、`path_0..N`、结果数量 |
| `trajectory.png` | 最新地图及轨迹快照 |
| `trajectory.svg` | 带图例、单位和场景系限制说明的图；与 PNG 放在同一目录 |
| `terminal_001.png` 等 | 各次终态时的累计轨迹快照，不覆盖上一终态 |
| `manifest.json` | 地图哈希/分辨率/原点、关联任务目录、全部真实结果、路径关联限制、校验问题和更新时间 |

每段原有 `tcp_navigation_...` 目录额外包含 `visualization.json`，指向对应可视化存档。现有 `tcp_events.jsonl`、工程 JSON 和运动参数保持原样。记录时间是客户端收到数据的时间，不冒充同步传感器采集时刻；反馈轨迹是定位估计，不是独立真值。

## 离线回放与交付

点击「回放日志 / 轨迹 NPZ」，可选择以前的 `tcp_events.jsonl`、新存档 `events.jsonl` 或提供的 live_view 生成的轨迹 `.npz`。新版存档旁边有 `map.npz` 时优先使用该副本。旧日志没有地图副本时使用随客户端提供的 619 图，需自行确认地图版本。

点击「保存轨迹图和数据」可导出回放图到独立 `navigation_replay_...` 目录；不会覆盖原日志。离线导入 NPZ 本身没有完整终态原文，不能从 `n_result` 推断成功，也不会虚构 result。原始 live_view NPZ 未保存完整结果，应同时保留当时控制日志。

交付时复制整个 `navigation_view_...` 或 `navigation_replay_...` 文件夹，连同对应工程 JSON/控制运行目录即可。轨迹 NPZ 也可交给原始 `replay_view.py`（那台机器仍需 NumPy/Matplotlib）；该原始脚本会把所有点连起来，新客户端则保留分段边界。

## 终点标注、可调距离与 GO 结果（2026-10-30 更新）

- 「导航点映射 / 控制」及「系统 2」页新增共享的 **BBOX 外侧距离 / m**。输入正数后点击「应用距离」，默认仍为 0.4。它改变的是导航参考点相对 BBOX 边界的候选距离，不是机身边缘净空，也不改速度、超时、到达容差。
- 修改后保留当前起点，清除旧终点核对状态，重新生成候选点；系统 2 的整队核对失效，需要重新生成并核对队列。活动导航、已授权队列或未知执行状态期间不能应用修改。
- 「导航地图 / 轨迹」中灰色 **P1/P2** 为候选终点（未发送），橙色 **G1/G2** 为请求中的实际终点。旁边的表格给出物体 ID、x/y/yaw、执行状态和原因。手工修改终点后点击「预览映射」刷新地图；系统 2 更新所选点后同步刷新。
- GO 返回终态后，控制页醒目文字、系统 2 逐段状态、地图页结果表同步显示。成功为绿色，失败为红色；PNG 标注后缀 S=成功、F=失败/拒绝、C=取消、U=未知。
- 只有 ROS status=4 且 success=true、reason=arrived 才显示“成功”；失败使用原 reason，例如 position_out_of_tol。取消单列，断线/未知状态不冒充失败终态或成功。按钮发送、规划通过、轨迹看似接近目标都不算成功。
- 每个请求都有唯一 request_id。可视化存档的 `tasks/task_001/` 等目录保存 `task.json`（完整请求及指令/工程文件引用）、`events.jsonl`、`outcome.json`（GO 原始事件 + 与界面相同的判定）、`trajectory.json` 与终态 `trajectory.png`。所有原始控制任务目录仍保留；不会因为下一条任务覆盖上一条结果。
- 为便于审计，请优先回放 JSONL 或交付整个目录。旧 live_view NPZ 不包含目标指令和完整 result，不能仅由它恢复所有执行结论。

## BBOX 环绕采样与导航栅格筛选（2026-10-30）

现在不再把靠近起点一侧的单一 BBOX 外侧点直接作为候选终点。每次生成时，先保留原投影候选，再绕物体采样 144 个方向，保持到 XY BBOX 边界的已选距离（圆角矩形外环）；按距当前起点由近到远筛选。

筛选使用窗口同一份 619 导航栅格。终点格必须为空闲，并检查以终点为圆心、半径 0.35 m 的圆是否与障碍格相交或越出地图。0.35 m 来自导航组提供代码的 inflate_radius，属于静态圆形近似，不是已验证的真实机身全姿态净空。不会自动放宽该半径。

没有候选通过时，窗口明确提示，不生成可发送终点；需要核对地图、改变窗口的 BBOX 距离或人工填写通过检查的点。不会自动把 0.4 m 改成更远的距离。有限采样未找到候选，不等于数学上证明整圈不存在可用点。

单目标、多目标、导航点 JSON 导入后的预览/发送，以及人工编辑点，都经过同一终点校验。修改源码后需重启客户端并重新生成候选队列；已有工程 JSON 无需再调用 API。多目标任何一段无合格点时整队不生成，清除旧队列授权与旧候选标记。

网格筛选不验证两张地图的实测配准，也不计算机器人路线；仍须现场确认语义图、619 栅格、狗端坐标系实际对齐。路线可达性由现有狗端规划负责，不声称通过终点检查就能保证到达。客户端的 pos_tol 仍为 0.05 m。

每次导航 dispatch_config.json 的 navigation_point_policy.navigation_grid_screening 记录筛选版本、地图哈希、栅格分辨率、圆形半径与终点格。候选预览事件同步保存这些证据；最终成功/失败仍依据 GO 原始结果。
