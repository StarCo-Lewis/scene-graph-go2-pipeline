# D3-619 狗端启动／重启

在 Windows 双击仓库根目录的 `启动或重启狗端服务.cmd`。依赖 Windows OpenSSH 的 ssh.exe / scp.exe，不调用 WSL。狗端需要 Python 3.8、已有的 nav_ws、619 地图和 `.token`。

1. 启动：没有服务时启动 CAPO、619 导航和网桥；有旧服务时显示状态，不重复启动。部分服务缺失时先检查，再选择重启。
2. 仅重启导航和网桥：保留运行中的 CAPO。修改导航源码后通常使用此项。
3. 全部重启：停止已识别的本用户 CAPO、导航和网桥，再按顺序启动。
4. 查看状态：检查进程及只读 TCP 握手，不发送 goal。

SSH / sudo 密码直接在终端输入，输入时不显示字符。脚本不保存密码。网桥共享口令从狗上的 `~/nav_ws/nebula_bridge/.token` 读取，不打印。

开始/重启前，确认狗已停止、客户端队列停止，再在狗端提示处输入 `STOPPED`。若网桥报告 busy，或存在 `runtime/pending_goal.json`，脚本会拒绝操作，保留原记录供人工核查。不会强杀不退出的进程，不删除任务状态，也不会自动再次尝试导航。

运行参数取自提供的《组2联调总手册》：619 栅格、CAPO scale 1.048、waypoint、DOMAIN 0，完整场景名保持不变。先验证只读网桥，再启用 `--allow-motion`；启动过程不发送导航目标，也不自动应用 4 cm 补丁。端口释放可能等待约 60 秒。

每次启动日志保存在狗端 `~/nav_ws/pipeline_service_logs/<时间>/`：`capo.log`（全启动时）、`navigation.log`、`bridge_readonly.log`、`bridge_motion.log`、`operation.json`。失败时保留已经启动的服务和日志，便于排查。

**重启导航会丢失原先坐标对齐。** 回到客户端后重新连接，在原场景坐标系测量当前位置作为第一次 s_*；不要把非原点位置填成 0。第一条目标建立对齐，后续多段保持既有客户端接续逻辑。

启动仅以日志、存活进程和 Action/网桥握手验证就绪，不代表定位精度、实际运动和避障已经实测通过。本脚本尚未在狗端验证。

## 4 cm 补丁的新版本

`configure_fine_stop_4cm.py` 已支持 `dist <= cfg.stop_radius_m`。之前出现 Unrecognized old threshold 时文件没有修改。需重新上传最新脚本；在狗停止、当前任务结束后执行：

```bash
python3 ~/configure_fine_stop_4cm.py ~/nav_ws/nav/control/fine_approach.py --apply
```

它只将位置阶段的停止比较改为 `dist <= 0.04` 并备份原文件，不改最终验收、速度或朝向逻辑。随后选菜单 2 重启导航和网桥。不要用本地整份旧导航源码覆盖狗端新版。
